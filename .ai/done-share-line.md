# `share_line` / `content_end` investigation

**Snapshot, and still load-bearing.** Written on `wt/share-line` at `8c75e00`,
2026-08-28. Nothing here has been superseded: `share_line` still measures from
the last child's `end` and the bug is still open. This note is the evidence
that `docs/onboarding/FINDINGS.md` entry 9 was wrong in three particulars, and
that entry now carries the correction and cites this file.

## Outcome

I stopped without changing either runtime. The proposed `content_end` unification
does correct the attachment decision for the FINDINGS 9 leaf, but it does not
produce correct output for a valid source-backed leaf. It replaces the current
stray comment gap with an invented blank line. The runtime and test experiments
were therefore removed; this note is the only committed change.

## Leaf repro

The valid frozen-tree shape uses source `a\n# c\n` and a leaf spanning `0..2`
whose text is exactly `"a\n"`. That exact text matters: frozen-tree leaves carry
their source bytes.

With the current code, both Rust and JS emit:

```text
a
 # c
```

That settles the conflicting descriptions in favour of the stray-leading-space
report for the valid shape (with the default one-column comment gap). The same
probe through the shipped Python package emits two leading spaces because
Python declares `comment_gap: 2`.

The `a # c\n` report is reproducible only with a hand-authored leaf whose
`text` is `"a"` while its range still ends at 2. That text/range pair disagrees
with the source and is not the frozen-tree shape generated by `gen_trees.py`.

After experimentally replacing the heuristic with `content_end`, both runtimes
emit:

```text
a

# c
```

The attachment correctly changes from suffix to own-line, but the leaf has
already emitted its swallowed newline. The own-line `after` comment then emits
its required hard break, producing two line endings. Correct output is
`a\n# c\n`; the boundary-only change does not reach it. A complete repair needs
to settle ownership/coalescing between a line terminator emitted by leaf content
and the structural break before an own-line comment. That is distinct from the
requested `share_line` substitution, so I followed the prompt's stop condition
instead of broadening the slice.

## Narrowing question

The objection in the prompt is correct, and grok's “suffix to own-line only”
claim is false. `content_end(parent)` can be greater than the last child's end
when source content belonging to an interior node is not represented by its
children. In that case the measured range narrows and can remove newlines.

This is reachable in a shipped grammar, not merely a synthetic tree. Parsing
the following with pinned `tree-sitter-toml==0.7.0`:

```toml
x = """a
b""" # c
```

produces a `pair` whose direct children are `bare_key`, `=`, `string`, and
`comment`. The `string` spans the whole multiline literal, but its only child is
the opening `"""`. Consequently:

- current boundary: opening delimiter end; the literal's internal newline is
  counted, so both runtimes wrongly render `# c` on its own line;
- unified boundary: the string's content end after the closing delimiter; no
  newline lies between that delimiter and `# c`, so both runtimes correctly
  render the comment as a suffix.

Thus the own-line to suffix direction is real and correct here: the newline the
old code counted belongs inside the previous item, not between that item and
the comment. The general argument for unification is not monotonicity. It is
that attachment must measure from the previous node's own content boundary;
the last-child heuristic can be wrong on either side of that boundary.

The existing Go `statement_list` case remains unchanged under the experimental
unification and its test passes. Its parent range adds only the terminating
newline, which `content_end(parent)` strips back to the last child's end.

I also scanned all frozen corpus trees with each shipped package's comment
kinds. At every actual comment attachment, `content_end(previous item)` equals
the current heuristic boundary. That independently explains the measured
zero-file corpus delta; it does not validate the leaf or TOML edge cases.

## Tests and changes

I built equivalent temporary Rust and JS regression pins beside the existing Go
test:

1. The valid leaf pin expects `a\n# c\n`. It demonstrates
   `a\n # c\n` before unification and `a\n\n# c\n` after it.
2. The shipped TOML narrowing pin expects the multiline string's comment to
   remain inline. It fails before unification and passes after it.
3. The existing Go pin passes after unification.

Because the requested implementation left the primary leaf pin failing, I did
not commit either the implementation or tests that would require asserting an
incorrect output. `rust/src/attach.rs`, `rust/src/eval.rs`,
`runtime-js/bundle.js`, and `runtime-js/bundle.test.js` are unchanged from
`main`; there was no FINDINGS file in this worktree to update.

## Disagreements with the prompt

- The prompt's narrowing objection is established, not merely possible.
- Grok's one-direction safety claim is wrong.
- The proposed unification is correct for attachment in both directions, but it
  is not by itself a correct FINDINGS 9 leaf fix because the renderer duplicates
  the swallowed line ending after the attachment flips.
- The valid leaf reproduces the stray-space symptom, not the pulled-up comment.
