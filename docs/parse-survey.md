# Parse-layer survey: the facts

Companion to `docs/parse-layer.md`. That document prices six routes; this one
establishes the facts the pricing rests on. It contains no recommendation.

Every number here is either a **measurement** (with the command that produced
it) or a **citation** (with a URL and fetch date) or an **estimate** (marked as
such, inline). Nothing else.

Measured on 2026-08-29 unless stated. Toolchain: `tree-sitter 0.26.8`,
`gcc (GCC) 15.2.0`, `node` + `npm` from nixpkgs, `gzip` 1.x, x86-64 linux.

## Corrections to `docs/parse-layer.md` and to this survey's own brief

Stated first and loudly, per instruction. Four other tracks are reasoning from
that document.

1. **`uv pip download` does not exist.** The brief (and any workflow derived
   from it) tells you to fetch grammar sources with
   `uv pip download tree-sitter-json==0.24.8 --no-binary :all: -d <dir>`. On the
   installed `uv` this is `error: unrecognized subcommand 'download'`. Fetch the
   sdist URL from the PyPI JSON API instead:

   ```sh
   curl -sSL https://pypi.org/pypi/tree-sitter-json/0.24.8/json |
     python3 -c 'import sys,json;d=json.load(sys.stdin);print(next(u["url"] for u in d["urls"] if u["packagetype"]=="sdist"))'
   ```

2. **The `scanner.c` claim in `parse-layer.md` is CORRECT, and it is broader
   than stated.** Verified by `tar tzf` over all 15 sdists this repo's pins
   name. Sdists shipping `parser.c` with **no** `scanner.c`: **python 0.25.0,
   yaml 0.7.2, css 0.25.0 — and also json 0.24.8 and go 0.25.0, which genuinely
   have no scanner.** So the finding is exactly the three the doc names. Every
   other pinned grammar's sdist ships `scanner.c` beside `parser.c`.

3. **A second sdist packaging gap the doc did not name.** Five sdists ship
   `src/tree_sitter/{parser,alloc,array}.h` (css, go, javascript, python, yaml);
   the other ten ship **no headers at all**, so their `parser.c` cannot be
   compiled from the sdist alone. The grammar's **git tag** does ship the header
   (`https://raw.githubusercontent.com/tree-sitter/tree-sitter-json/v0.24.8/src/tree_sitter/parser.h`
   is 7,039 bytes, fetched 2026-08-29). This matters to anyone planning an
   offline transcoder pipeline off sdists.

4. **`parse-layer.md`'s "the pins are ABI 14/15 era" is exactly right**, and the
   split is worth having by name — see the table in §2.

5. **A `parser.c` at ABI 14 generated by tree-sitter 0.24.x does not compile
   against tree-sitter 0.26.8's `parser.h`.** The _runtime_ ABI is
   backwards-compatible (`TREE_SITTER_MIN_COMPATIBLE_LANGUAGE_VERSION 13`), but
   the _header_ is not: 0.24-era `parser.c` initialises `.version` (renamed
   `.abi_version`) and names `TSFieldMapSlice` (renamed `TSMapSlice`) and
   `TSLexMode` (superseded by `TSLexerMode`). Build each grammar against the
   header from its own tag.

6. **`tree-sitter generate` silently downgrades to ABI 14 without a
   `tree-sitter.json`.** Observed: running `tree-sitter generate --abi 15` in a
   directory with `grammar.js` + `package.json` but no `tree-sitter.json` prints
   `Warning: No 'tree-sitter.json' file found in your grammar, this file is required to generate with ABI 15. Using ABI version 14 instead.`
   and emits ABI 14. A transcoder pipeline that shells out to the CLI will get
   ABI 14 output unless it writes that file.

## 1. Does tree-sitter expose the generated tables as data?

**Short answer: no supported path emits the tables as a data file — but
tree-sitter's own source contains a complete, authoritative, maintained routine
that copies every table out of a compiled grammar, and it is the strongest
existing evidence that the data/code split is clean and small.**

### 1a. The CLI has no dump/serialize flag

`tree-sitter 0.26.8`. Subcommands:
`init-config init generate build parse test version fuzz query highlight tags playground dump-languages complete`.
Every flag of `generate` was read:

| Flag                         | What it actually produces                                                                                                                                                                                                                |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--no-parser`                | `grammar.json` + `node-types.json` **only** — pre-table rule descriptions, not tables                                                                                                                                                    |
| `--json-summary`             | conflict report, not tables                                                                                                                                                                                                              |
| `--report-states-for-rule -` | a **count** of parse states per rule, nothing more. Measured on tree-sitter-json v0.24.8: `object 6 / array 6 / string 4 / object_repeat1 4 / array_repeat1 4 / pair 3 / _string_content 2 / document_repeat1 2 / document 1 / _value 1` |
| `--abi <VERSION>`            | 13–15; `--abi=latest` = 15                                                                                                                                                                                                               |
| `--disable-optimizations`    | disables parse-state merging                                                                                                                                                                                                             |

`dump-languages` prints the loader's _config_ (which grammars it knows about),
not tables. `parse --dot` / `--xml` / `--cst` dump **trees**, not tables.

**There is no `--dump-tables`, no `--emit-json`, no serialization flag anywhere
in the CLI.**

### 1b. The C API has no serializer

`lib/include/tree_sitter/api.h` at v0.26.8. Every `ts_language_*` entry point:

```
ts_language_copy  ts_language_delete  ts_language_symbol_count
ts_language_state_count  ts_language_symbol_for_name  ts_language_field_count
ts_language_field_name_for_id  ts_language_field_id_for_name
ts_language_supertypes  ts_language_subtypes  ts_language_symbol_name
ts_language_symbol_type  ts_language_abi_version  ts_language_metadata
ts_language_next_state  ts_language_name  ts_language_is_wasm
```

None of these returns a table. The only two that touch the parse table at all:

- **`ts_language_next_state(lang, state, symbol)`** — returns the successor
  state. Reading `lib/src/language.c:142`, for a **terminal** it returns
  `action.shift.state` of the _last_ action only, `0` for a reduce, and `state`
  itself for a `SHIFT_EXTRA`. So it is lossy in exactly the places that matter:
  it cannot tell you _what_ a reduce reduces to, cannot distinguish "no action"
  from "reduce", and collapses multi-action (GLR) entries.
- **the lookahead iterator** (`ts_lookahead_iterator_new/next/current_symbol`) —
  enumerates the _valid symbols_ in a state, not their actions.

So the brute-force route ("enumerate `state_count × symbol_count` through the
public API") recovers the **shift graph and the valid-symbol sets**, and loses
reduce symbol, child count, dynamic precedence, production id, `extra`,
`repetition`, and every ambiguity. That is not enough to rebuild a parser.

The Rust `tree_sitter` crate is a thin wrapper over exactly this set — the
public `impl Language` in `lib/binding_rust/lib.rs` is
`new, name, abi_version, metadata, node_kind_count, parse_state_count, supertypes, subtypes_for_supertype, node_kind_for_id, id_for_node_kind, node_kind_is_named, node_kind_is_visible, node_kind_is_supertype, field_count, field_name_for_id, field_id_for_name, next_state, lookahead_iterator`.
**No serializer, no table accessor.**

### 1c. `TSWasmStore` changes the picture — this is the finding

`lib/src/wasm_store.c` (1,940 lines) implements `ts_wasm_store_load_language`.
To make a wasm grammar usable, it must reconstruct a host-side `TSLanguage` from
a grammar compiled to wasm32. It does this by **copying every data table out of
the module's linear memory**, and replacing **only the function pointers** with
wasm-call trampolines.

That routine is therefore a maintained, upstream, exhaustive statement of which
`TSLanguage` fields are data and which are code — and it ships **sizing formulas
for every table**, which are otherwise nowhere written down. Extracted verbatim
from `wasm_store.c` (v0.26.8):

| Field                         | Element size formula                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------------- |
| `parse_table`                 | `large_state_count * symbol_count * 2`                                                       |
| `parse_actions`               | unsized — walked via `copy_unsized_static_array` against the module's data-segment addresses |
| `symbol_names`                | `symbol_count + alias_count` C strings                                                       |
| `symbol_metadata`             | `(symbol_count + alias_count) * sizeof(TSSymbolMetadata)`                                    |
| `public_symbol_map`           | `(symbol_count + alias_count) * 2`                                                           |
| `lex_modes`                   | `state_count * sizeof(TSLexerMode)`                                                          |
| `field_map_slices`            | `production_id_count * 4`                                                                    |
| `field_map_entries`           | `max(slice.index + slice.length)` entries                                                    |
| `field_names`                 | `field_count + 1` C strings                                                                  |
| `supertype_symbols`           | `supertype_count * 2`                                                                        |
| `supertype_map_slices`        | `(max supertype id + 1) * 4`                                                                 |
| `supertype_map_entries`       | `last_slice.index + last_slice.length`                                                       |
| `alias_map`                   | walked: `(symbol, count, count×TSSymbol)*` terminated by symbol 0                            |
| `alias_sequences`             | `production_id_count * max_alias_sequence_length * 2`                                        |
| `small_parse_table_map`       | `(state_count - large_state_count) * 4`                                                      |
| `small_parse_table`           | unsized — walked like `parse_actions`                                                        |
| `primary_state_ids`           | `state_count * 2` (ABI ≥ 14)                                                                 |
| `name`                        | C string (ABI ≥ 15)                                                                          |
| `reserved_words`              | `(max reserved_word_set_id + 1) * max_reserved_word_set_size * 2` (ABI ≥ 15)                 |
| `external_scanner.symbol_map` | `external_token_count * 2`                                                                   |

and the fields it **cannot** copy, which it leaves as wasm function indices:

```
lex_fn
keyword_lex_fn
external_scanner.create
external_scanner.destroy
external_scanner.scan
external_scanner.serialize
external_scanner.deserialize
```

Seven function pointers. `external_scanner.states` is data (a
`bool[n][external_token_count]`) but is left as a wasm _address_ because it is
read from inside the module.

**What this means, stated without a recommendation:** the "dump the tables as
data" step of any transcoding route does not have to be invented. Upstream
already does it — from wasm, not from `parser.c` — and the routine names every
field and its size. The step that upstream does _not_ do, and cannot, is the
seven function pointers. Six of those seven are the external scanner. The
seventh is `lex_fn`, which is §3.

**ABI 14 → 15 differences**, from `lib/src/language.h:13-14`

`TSLexerMode {lex_state, external_lex_state, reserved_word_set_id}`. ABI 13 → 14

code. **The data/code boundary is stable across every ABI this project
touches.**

### 2b. What fraction of a grammar is data?

**Method.** Compile each `parser.c` alone, `cc -Os -c -I <its own header dir>`,
and attribute every byte of `.text` + `.rodata*` + `.data*` to a named symbol
via `nm -S --defined-only -t d` and `size -A`. Script: `regions.py` (reproduced
in §2d). `.comment`, `.eh_frame` and `.note.*` are excluded as toolchain
overhead.

**Caveat, stated up front: this is x86-64 code size, not wasm code size.** The
_ratio_ transfers approximately; the absolute code bytes do not. Treat the
percentages as a ranking and an order of magnitude, not as a wasm forecast.

**There is no single "fraction of a grammar is data" number, and anyone quoting
one is wrong.** The honest statement is a range and its shape:

- For the **big** grammars — the ones whose download cost is the problem — the
  answer is **95–99.6% data**. rust, typescript, haskell, python, javascript,
  go, kotlin, ruby, yaml are all ≥ 95%.
- The exceptions are **small grammars** (json 31%, html 34%, toml 36%, xml
  27–32%), where the lexer is a near-fixed cost against tiny tables, and **two
  genuine outliers**:
  - **css 0.25.0 — 57.3% code.** 437 lex states, and its lexer emits long inline
    character-range comparison chains rather than `set_contains` tables (only
    160 bytes of `TSCharacterRange` across the whole grammar).
  - **markdown 0.5.1 — 44.3% / 38.6% code.** Its `parser.c` lexer is large in
    both halves.
- And the mirror outlier: **yaml 0.7.2 is 0.1% code.** Its `ts_lex` has
  **exactly two states** (`ACCEPT_TOKEN(ts_builtin_sym_end)` and an EOF
  advance). _Every_ YAML token comes from the external scanner. Recovering
  `ts_lex` as data buys nothing at all for YAML; conversely a scanner VM buys
  everything.

Lex-state counts, for scale (`awk` over the `ts_lex` body, counting `case N:`):
json 44, go 165, css 437.

### 2d. Reproducing §2b/§2c

```sh
# 1. sources
curl -sSL https://pypi.org/pypi/tree-sitter-go/0.25.0/json |
  python3 -c 'import sys,json;d=json.load(sys.stdin);print(next(u["url"] for u in d["urls"] if u["packagetype"]=="sdist"))' |
  xargs curl -sSLO
tar xzf tree_sitter_go-0.25.0.tar.gz

# 2. compile parser.c alone against its own header
cc -Os -c -I tree_sitter_go-0.25.0/src tree_sitter_go-0.25.0/src/parser.c -o go.o

# 3. attribute
size -A go.o
nm -S --defined-only --size-sort -t d go.o
```

For a grammar whose sdist ships no `src/tree_sitter/`, take the header from the
grammar's git tag:

```sh
mkdir -p h/tree_sitter
curl -sSL -o h/tree_sitter/parser.h \
  https://raw.githubusercontent.com/tree-sitter/tree-sitter-json/v0.24.8/src/tree_sitter/parser.h
cc -Os -c -I h tree_sitter_json-0.24.8/src/parser.c -o json.o
```

## 3. `ts_lex`: every construct the generator can emit

Source of truth: `crates/generate/src/render.rs` at tree-sitter v0.26.8 —
`add_lex_function` (line 835), `add_lex_state` (867),
`add_character_range_conditions` (1049), `add_character_set` (1113),
`add_advance_action` (1149), `add_character` (1914) — plus the macro definitions
in `lib/src/parser.h`.

**Cross-checked empirically**: every statement in all **29** `ts_lex` /
`ts_lex_keywords` bodies across the 18 pinned grammar variants was classified
against the list below. **10,227 lex states, 15,510 conditional `ADVANCE`s, 480
conditional `SKIP`s, 405 `ADVANCE_MAP` blocks, 2,956 `ACCEPT_TOKEN`s, 122 EOF
advances — zero statements unclassified, zero condition atoms unrecognised.**
The construct set below is closed.

### 3a. The function skeleton — always exactly this

```c
static bool ts_lex(TSLexer *lexer, TSStateId state) {
  START_LEXER();
  eof = lexer->eof(lexer);
  switch (state) {
    case 0:
      <state body>
    ...
    default:
      return false;
  }
}
```

`START_LEXER()` (from `parser.h`) expands to the loop scaffolding: declares
`result=false, skip=false, eof=false, lookahead`, then `goto start;` /
`next_state: lexer->advance(lexer, skip); start: skip = false; lookahead = lexer->lookahead;`.
`ADVANCE(n)` = `state = n; goto next_state;`. `SKIP(n)` =
`skip = true; state = n; goto next_state;`. `END_STATE()` = `return result;`.

`keyword_lex_fn` is emitted by the **same** function under the name
`ts_lex_keywords`, so it has an identical shape.

### 3b. State body — the ordered grammar

Per `add_lex_state`, in this order, each part optional except `END_STATE`:

1. `ACCEPT_TOKEN(sym);` — at most one, **first**. Also expands `mark_end`. This
   is the longest-match mechanism: accept, then keep trying to advance.
2. `if (eof) ADVANCE(n);` — at most one.
3. `ADVANCE_MAP(c0, s0, c1, s1, …);` — at most one, emitted **only** when the
   leading run of single-character (or two-adjacent-character) main-token
   transitions covers **≥ 8 ranges**. It expands to a static `uint16_t map[]`
   plus a linear scan.
4. Zero or more transition statements (below).
5. `END_STATE();`

### 3c. Transition statements — four shapes, and only four

```c
ADVANCE(n);                 // unconditional (simplified char set became empty)
SKIP(n);                    // unconditional, and does not extend the token
if (<cond>) ADVANCE(n);
if (<cond>) SKIP(n);
```

**Note for a mechanical recoverer**: the unconditional `ADVANCE(n);` /
`SKIP(n);` forms occur **zero times** in all 18 pinned grammars, but the
generator can emit them — `add_lex_state` comments that `simplify_ignoring` "may
result in an empty character set… that means the transition is guaranteed".
Handle them; do not assume they cannot appear.

### 3d. Condition atoms — seven shapes, and only seven

`add_character_range_conditions` walks the character set's ranges. In
**positive** mode atoms join with `||`; in **negative** mode with `&&`.

| #   | Emitted C                            | Meaning                                                          | Observed count |
| --- | ------------------------------------ | ---------------------------------------------------------------- | -------------: |
| 1   | `lookahead == X`                     | single char (also emitted twice, `A \|\| B`, for a 2-char range) |         14,790 |
| 2   | `(A <= lookahead && lookahead <= B)` | inclusive range                                                  |          4,453 |
| 3   | `lookahead != X`                     | negated single char (twice for a 2-char range)                   |            996 |
| 4   | `set_contains(NAME, N, lookahead)`   | binary search over a `static const TSCharacterRange NAME[]`      |            750 |
| 5   | `(lookahead < A \|\| B < lookahead)` | negated range                                                    |            232 |
| 6   | `lookahead > B`                      | negated range starting at `\0`                                   |            127 |
| 7   | `(!eof && …)`                        | EOF guard, wrapping atom 1 or 4 when the set contains `\0`       |             35 |

An eighth exists in the generator but did not occur in this sample:
`(!eof && lookahead <= B)` — the positive form of atom 6, emitted when a
positive range starts at `\0` and does not end there.

**Combination rule.** When a transition uses both a large set and extra checks,
`add_lex_state` emits
`if ( (set_contains(...) || <positive atoms>) && <negative atoms> ) ACTION;` —
the parenthesised positive group, `&&`, then the negatives.

**The is-included flip, and it is a trap.** If the positive character set
contains `char::MAX`, the generator _negates the set, adds `\0` back_, and emits
it in **negative** form (atoms 3/5/6 joined by `&&`) — inside what is logically
a positive condition. A recoverer that assumes "`||` means union of accepted
characters, `&&` means exclusion" will invert the meaning of every such state.
The tell is a whole condition composed of `!=` / `<..||..<` / `>` atoms with no
positive atom and no `set_contains`.

### 3e. `set_contains` and its tables

`set_contains(ranges, len, lookahead)` is a `static inline` binary search
defined in `lib/src/parser.h`, emitted into `.text` as a real function when the
compiler declines to inline it (measured: 74 B in `go.o` at `-Os`). Its tables
are emitted by `add_character_set` as

```c
static const TSCharacterRange sym_identifier_character_set_1[] = {
  {'A', 'Z'}, {'_', '_'}, …
};
```

with `TSCharacterRange { int32_t start; int32_t end; }`. These are **already
data** — 8 bytes per range. Measured in go 0.25.0:
`sym_identifier_character_set_2` 6,400 B (800 ranges),
`sym_identifier_character_set_1` 5,480 B (685 ranges),
`sym_rune_literal_character_set_1` 88 B. Unicode identifier classes are the
usual content. Unused sets are **not** emitted (`info.is_used` gate).

### 3f. Character literal rendering (`add_character`)

`'\''` `'\\'` `'\f'` `'\n'` `'\t'` `'\r'` are escaped; `\0` becomes bare `0`;
`' '` and ASCII-graphic become `'c'`; everything else becomes `0x%02x` —
including 4- and 6-hex-digit values for non-BMP, e.g. `0x2192` in haskell.

**Two lexing traps for anyone parsing `parser.c` textually:**

- Character literals contain `'('`, `')'`, `';'`, `','`, `'\''`, `'\\'`. Any
  regex or line splitter that is not literal-aware will mis-split `ADVANCE_MAP`
  blocks and long conditions. This bit the first version of the script above;
  masking `'(?:\\.|[^'\\])'` first fixes it.
- **A generator bug produces `lookahead == 00`** (two zeros). In
  `add_character_range_conditions`, the `start == '\0' && end == '\0'` branch
  writes the literal string `"lookahead == 0"` and then falls through to
  `self.add_character(end)`, which appends another `0`. It is harmless in C
  (`00` is octal zero) but a naive tokenizer will trip. Occurs twice, in
  **tree-sitter-python 0.25.0** (`src/parser.c`). This also confirms the reading
  of `render.rs` above is exact rather than approximate.

### 3g. What is _not_ in `ts_lex`

The lexer's interaction with the outside is entirely through the `TSLexer`
vtable: `advance`, `mark_end`, `get_column`, `is_at_included_range_start`,
`eof`, `log`. `ts_lex` calls only `advance` (via `ADVANCE`/`SKIP`), `mark_end`
(via `ACCEPT_TOKEN`) and `eof`. `get_column` and `is_at_included_range_start`
are used **only by hand-written external scanners**, never by generated code. So
a recovered `ts_lex` needs a runtime offering exactly three operations.

at failIf (node_modules/web-tree-sitter/web-tree-sitter.js:1927)

### 5c. Lezer — and `@lezer/lr` alone is not the runtime

**Correction to `docs/parse-layer.md` and `docs/design.md`.** Both quote
"17.5 KB (`@lezer/lr`)" as the Lezer runtime. `@lezer/lr` 1.4.10's own
`dist/index.js` is indeed 17,564 B gz — but it **does not contain a parser
runtime on its own**: its `dependencies` are `{"@lezer/common": "^1.0.0"}` and
its dist file opens with `from '@lezer/common'`. `@lezer/common` 1.5.2 is a
further 20,364 B gz unbundled. Every grammar additionally pulls
`@lezer/highlight`.

The honest figure is a **tree-shaken bundle**, which is both more accurate and
kinder to Lezer than naive addition. Measured with `esbuild --bundle --minify
--format=esm`, then `gzip -9`:

| Bundle | raw | gz |
| --- | ---: | ---: |
| runtime only (`import {LRParser} from "@lezer/lr"`) | 45,782 | **14,953** |

So the real Lezer runtime floor is **~14.6 KiB gz**, *below* the 17.5 KB
commonly quoted. The 17.5 KB number is the unbundled dist of one package —
neither the floor nor the whole runtime. Use 14,953.

Per-language, bundling `import {parser} from "@lezer/<lang>"` (which transitively
pulls the runtime, `@lezer/common` and `@lezer/highlight`):

Two Lezer facts worth having:

- **`@lezer/markdown` does not use `@lezer/lr` at all.** Its dependencies are
  `@lezer/common` and `@lezer/highlight` only; it is a hand-written incremental
  block/inline markdown parser, not a generated LR table. So "Lezer markdown"
  is not evidence that a table-driven route handles markdown.
- **No `@lezer/ruby` or `@lezer/haskell` exists on npm** (`npm pack` fails for
  both). Lezer covers 10 of this project's 17 languages at most.
