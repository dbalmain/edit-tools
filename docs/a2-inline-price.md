# What A2 costs, measured before any of it was built

`docs/prose-projection.md` schedules A2 as five slices and quotes a payoff for
each. This is where those figures come from: a feasibility spike run on
`spike/a2-price` against the frozen commit
`f2819822fa033987e86db79143ab8ffecb900a35`, which priced the inline grammar,
ported its scanner, and classified every paragraph A1 refuses -- before a line
of A2 was written.

It is a **dated measurement**, not a live one. Everything below is as it read at
that commit; where the tree has since moved, the next section says so rather
than the figures being quietly restated. Nothing here was remeasured to make it
agree with today.

## Executive summary: price and shape

- Scanner-port price: **9,130 B source / 462 B packed**, with no new VM opcode
  found; replay is green over 8,631 calls. Budget **0.5–1 day** for production
  review/fuzz/trace landing.
- Inline grammar blob/runtime price: **450,325 B raw / 43,110 B gzip** for the
  transcoded blob including the 462 B scanner. That alone is +218% over the
  measured 19,770 B formatter runtime; the effective separate-asset payload
  becomes 62,880 B.
- Real A2 construct coverage: **2,532 of the 2,553 `inline token` refusals
  (99.2%) are safe-only**, giving 3,068 paragraphs / 60.6% including A1. If A2
  retains A1's ASCII-only policy, that falls to 2,168 / 42.8%; this policy fork
  must be explicit in the brief.
- Main hidden difficulty: **safe constructs do not imply safe breaks**. All six
  inline-reparse stress patterns preserve all 2,532 safe-only inline trees, but
  naive whole-paragraph gap flipping changes the standalone block parse for 138
  of them. Range plumbing is already available by slicing; grammar tables, at
  43,110 B gzip, are the large shipping price.
- Recommended slicing: **A2.0 loader/dual-parse plumbing; A2.1 ASCII code spans
  and links protected whole; A2.2 emphasis/strong with grammar-confirmed gaps
  and a block-reparse gate; A2.3 Unicode text policy; A2.4 deferred
  constructs.** Details in section 5.

## 1. Inline scanner port

### Pipeline audit: generic versus block-specific

The pipeline is reusable but not fully grammar-agnostic as checked out at
`f281982`:

- `ts_scanner_build.mjs`, the assembler, packer, and VM are scanner-name/data
  driven. Once a `.program.js` exists, `ts_scanner_build.mjs markdown_inline`
  produced the `.svm` without runtime changes.
- The pipeline does **not** compile C automatically. A `.program.js` is a
  reviewed hand-port of `scanner.c`; that is the actual port cost.
  `ts_scanner_record.py` records the C oracle but does not produce VM bytecode.
- The recorder selected only the manifest's `grammar_symbol = "language"`, hence
  the block grammar. An experimental `--grammar-symbol inline_language` override
  was added for this spike.
- That override exposed a second assumption in `ts_grammars.wanted`: it
  understood `language_inline`, not the binding's real `inline_language`
  spelling. The spike teaches it both spellings.
- Replay originally equated scanner artifact name, trace-directory name, and
  corpus-directory name. Experimental `--trace-dir` and `--source-language`
  overrides were needed to replay `markdown_inline.svm` against traces generated
  from `corpus/src/markdown`.

Thus the VM/package format is grammar-agnostic, but the checked-out
orchestration is one-grammar-per-manifest and therefore block-specific for
Markdown. The plumbing repair is small; authoring/verifying the bytecode remains
manual.

### Inline scanner source and build procedure

Source: PyPI sdist `tree-sitter-markdown==0.5.1`, fetched by the repository's
`ts_grammars.py`; `harness/wasm/grammars.tsv` records upstream tag `v0.5.1` and
tree hash `2dfd57f547f06ca5631a80f601e129d73fc8e9f0`. The fetched scanner is 397
physical lines and 15,883 bytes; generated `parser.c` is 2,259,663 bytes and
declares ABI 15 / 15 external tokens.

The experimental hand-port is `harness/scanners/markdown_inline.program.js`;
`node harness/ts_scanner_build.mjs markdown_inline` produced
`harness/scanners/markdown_inline.svm`. Neither is wired into a manifest or
shipped path.

### VM capability gap

**No missing VM capability was found.** The inline scanner needs lookahead,
`advance(false)`, `mark_end`, `eof`, indexed `valid_symbols`, branches/calls,
integer comparison/add/subtract, bitwise AND/OR, token emit/fail, and four
persistent `uint8_t` fields. Every operation already exists. `uint8_t` counter
overflow is expressed as `ALUI AND 0xff`; the ASCII CommonMark punctuation test
is one class table.

The C `malloc(sizeof(Scanner))` / `free` lifecycle does not require an opcode:
VM registers are the scanner instance. Upstream serialisation is exactly four
raw `uint8_t` values; the VM serialises the four persistent registers as signed
LEB128. Bytes differ by design, but replay checks a bijection between upstream
and VM states. All four values are bounded to 0..255, so the VM form is at most
eight bytes, far below tree-sitter's 1,024-byte state cap. No stack, string
buffer, recursion, libc classifier, range-start query, or new serialisation
shape is required.

|---|---|---|---|

| `ts_verify_lex.py` | PASS | 2,247 lexer states × 117 codepoint classes = 790,944 runs | 0 disagreements |
| `ts_verify_blob.py` | PASS | 83,595 table entries compared with compiled C memory | Every entry agrees |
| `ts_scanner_build.mjs --check` | PASS | Re-encode packed scanner | 462-byte artifact is current |

The recorder reported 17,451 trace records; replay's 8,631 figure counts scan
calls, while 189 counts serialisations. The remainder are deserialisations and

### Scanner-port estimate

The measured port is 282 lines of commented assembler source, 428 bytes of
executable VM code, one eight-range ASCII punctuation class, and a 462-byte
packed artifact. It required **zero VM/runtime changes**. The checked-in spike
port is complete enough to replay every observed scanner call, not merely a size
extrapolation.

Production price: **half a day to one day** to review the hand translation,
retain the secondary-grammar plumbing in a deliberate manifest shape, commit
inline-specific traces, and add delimiter/error fuzz cases. The principal
remaining uncertainty is oracle breadth: the 24 clean corpus files exercise
8,631 calls, but no dedicated malformed/delimiter-run fuzz corpus was added.
This is a day-shaped port, not a week-shaped VM extension.

The inline row is compact JSON from `ts_transcode.py`, generated from the 0.5.1

therefore includes the 462-byte scanner as base64. It has 1,161 parse states,

The like-for-like block blob is 469,172 B raw / 48,893 B gzip. Inline is 96.0%
of its raw size and 88.2% of its gzip size: it is a second grammar, not a small
appendix. Against the brief's stale 18,676 B runtime figure the effective total
would be 61,786 B, still +230.8% / 3.31×. The JS driver code itself does not
grow merely because it receives a second data blob; the cost is required
Markdown-page data.

### Can `ts_lr.mjs` drive two grammars over one document?

Yes, sequentially. `parse(blob, sourceBytes)` constructs a `Language` and
`Parser` from the blob for each call; it has no singleton language state.
Loading block and inline blobs under distinct keys and calling the same parser
entry point for each is supported today. The spike exercised that path for every
coverage candidate.

### Range / included-range second pass

There is no range parameter in `ts_lr.mjs`: `Parser` constructs `Lexer(bytes)`
at position zero, EOF is the end of that view, and `atRangeStart()` is
hard-coded as `lexer.pos === 0`. Therefore the manifest's literal statement is
correct: this is not tree-sitter's included-range facility.

But top-level A2 paragraphs are contiguous ranges, so true included ranges are
unnecessary. `ts_inject.mjs` already proves the cheaper route for fenced guests:

1. take `source.subarray(start, end)` (a zero-copy `Uint8Array`/`Buffer` view);
2. call `parseRoot(inlineBlob, slice)` as a standalone document;
3. add `start` to every returned byte offset before attaching/associating the
   tree.

The inline scanner does not call `is_at_included_range_start`;
reset-at-slice-start is the correct scanner lifetime. `probe_a2_driver.mjs` ran
this exact route for all **2,553** target ranges and found **zero**
native/browser construct, error-status, or rebased-root-range mismatches.

Copying a substring is semantically equivalent for this grammar too, but JS need
not copy. Native Python `bytes[start:end]` does copy; that is small for
paragraph-sized inputs, or native can use tree-sitter ranges later if profiling
justifies it. Disjoint container ranges remain a separate future problem and are
not A2's top-level shape.

### Cost of the second pass

There is **no range-aware lexer/parser project** in A2. The required work is
orchestration: declare/fetch a secondary blob, create/cache the secondary
language/parser, walk block `inline` nodes, parse slices, reject dirty inline
roots, rebase/associate offsets, and keep the syntax tree separate from the
formatter projection. Existing injection code supplies the pattern, though A2
should factor rather than pretend an inline pass is a guest-language injection.

Estimate this plumbing at **one to two days across native + browser + parity
tests**, with loader/schema design the part most likely to expand. A true
included-range implementation should remain deferred until containers require
disjoint retained ranges.

## 3. Corpus coverage

### Corpus identity and denominator

Corpus: every path ending `.md` in `git ls-tree -r
f2819822fa033987e86db79143ab8ffecb900a35`, read from that commit with `git
show`. This is 103 tracked files. The pinned 0.5.1 block grammar parses 102
cleanly; `docs/parse-survey.md` is excluded because its block root has an error,
exactly as the existing prose probe does.

The 102 clean files contain **5,065 paragraph nodes** at any nesting depth. A1's
top-level walk reaches 3,210 of them and deliberately stops at containers; its
first-match results are 2,553 `inline token`, 536 eligible, 70 non-ASCII, 30
block acquisition, 18 single atom, 2 whitespace run, and 1 byte. The target set
is exactly those 2,553 first-match `inline token` paragraphs, using the block
tree's sole `inline` child range. It does not include container paragraphs.

### Bucket definitions

The primary histogram is **paragraph presence**, multi-label: a paragraph
containing ten code spans contributes one to `code_span`, not ten. Exact 0.5.1
public node mappings are:

- emphasis = `emphasis`;
- strong emphasis = `strong_emphasis` (both grammar symbols canonicalise to that
  public name);
- code span = `code_span`;
- inline link = `inline_link`;
- autolink = `uri_autolink` or `email_autolink`;
- outside-safe = `backslash_escape`, `entity_reference`,
  `numeric_character_reference`, `shortcut_link`, `full_reference_link`,
  `collapsed_reference_link`, `image`, `html_tag`, `hard_line_break`,
  `strikethrough`, or `latex_block`;
- helpers ignored as independently meaningless = root `inline`, `link_label`,
  `link_destination`, `link_title`, `link_text`, `image_description`, and the
  emphasis/code/latex delimiter nodes;
- parse error = `root.has_error`; unclassified = any other named node not in the
  complete lists above;
- `safe-only` = clean inline parse and every meaning-bearing named node belongs
  to the five requested construct families. The set may be empty: anonymous
  punctuation which the inline grammar leaves literal is ordinary text, recorded
  separately as `literal-token-only`;
- `genuinely hard` = cannot safely be made atomic/protected using only its local
  inline range, or can change the block parse merely by moving it to a line
  boundary. This is narrower than “outside this brief's safe list”.

Plain text, anonymous literal punctuation, and ASCII spaces/newlines are not
constructs. Backslash escapes and entities are constructs outside the requested
set rather than silently counted as text. GFM extended autolinks such as bare
`https://...` are not represented by this grammar; A1 already admits them when
their characters pass its whitelist, so they do not occur in this target set.
Angle-bracket autolinks are represented and counted.

### Coverage caveats and validation

Every target was parsed twice: native tree-sitter for classification, then the
browser LR driver over the same byte slice. All 2,553 construct sets,
clean/error verdicts, and constant-rebased root ranges agree.

For safe-only paragraphs, the probe protects whole code spans, inline links, and
autolinks, then flips every remaining isolated ASCII space/newline through A1's
six adversarial patterns. **All 2,532 inline tree shapes remain identical**.
This is evidence that the named inline subset survives gap flips; it is not yet
a formatter projection.

The block side is the warning: parsing each paragraph slice as a block document,
naive flipping of every candidate gap changes the block shape for **138 of 2,532
(5.45%)**. Typical causes are a newly line-leading `=`, list/thematic marker, or
backtick sequence. This diagnostic is intentionally conservative and is not
subtracted from coverage: production can coalesce across only the hazardous gaps
and still reflow the rest. It does prove that “recognized safe construct” cannot
be the complete eligibility predicate. A2 needs the block-acquisition filter and
whole-document gate the design already demands.

The pinned inline grammar does not model GFM extended autolinks, and the pinned
block grammar is blind to pipeless GFM tables. Independent renderer/gate
coverage remains required for those known holes. `E2-COVERAGE.json` records
`ascii_text`, candidate-gap count, inline stress result, and standalone-block
diagnostic per paragraph so none of these qualifications is hidden in the
headline.

## 4. Native-side feasibility check

The 0.5.1 Python binding exports both `language()` and `inline_language()` and
maps them to `tree_sitter_markdown()` / `tree_sitter_markdown_inline()`. That
part of the brief is correct, except that calling it a Rust-crate export is
imprecise in this repository: `gen_trees.py` is Python and loads the Python
binding.

“One call” is false as a work estimate. `manifest.parser_for()` creates exactly
one parser from a manifest's one `grammar_symbol`, and `gen_trees.parse_doc()`
parses once before `convert()`. Native A2 must represent a secondary grammar,
create/cache a second parser, locate every block `inline` range, parse each
slice, reject dirty trees, rebase offsets, and associate the inline CST without
replacing the block CST. Existing injection `Region`/`convert(base=...)` code
demonstrates slice-and-rebase, so no native parser algorithm is needed; the
missing work is loader/orchestration and the formatter-view ownership described
in the design.

## 5. Recommended A2 slices

Do not write one A2 brief that says “add the inline grammar and widen the
predicate”. It hides a 43 KB product decision, a 900-paragraph Unicode decision,
and the block-safe-gap work behind one verb. Cut it this way:

### A2.0 — secondary grammar foundation, invisible

Scope: formalise a secondary-grammar declaration; retain the experimental inline
scanner after review/fuzz; generate/load the inline blob; add cached
native/browser second-pass orchestration over contiguous `inline` slices; reject
dirty roots; prove constant rebasing and producer parity. Do not project or
change output.

Payoff: no visible paragraph gain, deliberately. It isolates the parser/data
risk. Exit criterion: the two producers agree on all 2,553 audited ranges,
scanner replay and lexer/table oracles stay green, malformed inline fixtures
refuse identically, and the web payload/performance decision explicitly accepts
43,110 B gzip.

Estimated engineering work: **1.5–3 days**, including the **0.5–1 day** scanner
hardening. The range mechanism is slice + rebase, not included ranges.

### A2.1 — protected syntax on ASCII text

Scope: admit code spans, inline links, and autolinks; protect each whole,
including internal spaces/delimiters; admit grammar-confirmed literal
punctuation; retain the ASCII-only policy. Select only gaps which also preserve
the block parse, coalescing across hazardous ones.

Payoff ceiling under the measured definitions: 839 construct-safe candidates, or
**836 with at least one useful candidate gap**, taking total eligibility from
536 to **1,372 / 27.1%**. Thirty-five paragraphs in this subset fail the
deliberately naive all-gap block diagnostic, so block-safe coalescing is already
required here.

Exit criterion: source partition is total, six inline stress patterns preserve
inline structure, a whole-document block gate preserves block structure,
native/browser projections agree, and formatting is idempotent. Estimated
projection/gate work: **1–2 days after A2.0**.

### A2.2 — emphasis and strong emphasis, still ASCII

Scope: add emphasis/strong; delimiters attach to adjacent atoms rather than
becoming fill items; allow grammar-confirmed gaps inside emphasis; retain
protection for code/link ranges and retain the ASCII policy.

Payoff: another **791** useful-gap candidates under the measured policy,
reaching **2,163 / 42.7%** total. This is where global fill behavior and
delimiter-adjacency tests belong; keeping it separate makes failures
attributable.

Exit criterion: same gates as A2.1, plus nested/mixed emphasis, delimiter runs,
punctuation flanks, and reparse stability. Estimated work: **2–3 days**.

### A2.3 — Unicode text policy

Scope: admit non-ASCII atom content while continuing to recognise only ASCII
space/newline as breakable gaps. Do not claim Unicode line breaking; bytes
inside atoms stay opaque and exact. Add NBSP, combining-mark, astral,
invalid-boundary, and mixed-script cases.

Payoff: **900** additional safe-only candidates, bringing useful-gap coverage to
3,063; including the five safe-only/no-gap paragraphs as structurally eligible
gives the headline **3,068 / 60.6%**.

Exit criterion: both runtimes agree on UTF-8 byte ranges and displayed widths,
no non-ASCII byte can be split, and the semantic reparse gate remains
independent. Estimated work: **1–2 days**, mostly proof and tests rather than
parsing.

### A2.4 — deferred known constructs

Protect atomic backslash escapes/entities first (7 paragraphs), then decide
images/reference links (6) and strikethrough (4). Leave the four HTML paragraphs
refused until line-start HTML/comment reclassification has a specific rule and
gate. This slice buys little corpus coverage; it should not delay A2.1–A2.3.

The resulting price is **roughly 5.5–10 focused engineering days** for the
safe-set feature, of which the scanner is at most a day. That is an estimate
from measured code/data/test surfaces, not elapsed-time telemetry. A2 is
week-shaped, but not for the reason in the brief.

## 6. Risks, unknowns, and conclusion

The one issue most likely to make A2 harder than assumed is **gap qualification
across the block and inline grammars**, not the inline scanner and not included
ranges. Recognition is easy: 99.2% of the target paragraphs contain only the
requested construct families, and all six inline stress patterns preserve their
inline trees. Safe layout is harder: 138 construct-safe paragraphs change
standalone block shape when every apparent gap is naively allowed to flip. A2
must retain/coarsen atoms at hazardous boundaries and prove whole-document block
equivalence independently.

Measured conclusions:

- Scanner: fits unchanged, 462 B, green oracle; day-shaped.
- Tables: 43,110 B gzip, 2.18× the measured formatter runtime by themselves;
  this is the product/distribution price.
- Second pass: no true included-range work for A2; existing zero-copy slice +
  constant rebase works and agrees 2,553/2,553.
- Coverage: 2,532/2,553 construct-safe; only 21 outside scope, only four locally
  hard HTML cases; headline total 3,068/60.6% if Unicode atom text is included.

Remaining uncertainties:

- scanner replay has no dedicated malformed/delimiter fuzz corpus, so “no
  missing opcode” is stronger than the current coverage oracle, while bytecode
  correctness is only as broad as 8,631 observed calls;
- the secondary-grammar manifest/package schema is not designed here;
- performance needs a product threshold: the unoptimised per-slice browser path
  parsed and classified 856,716 bytes across 2,553 ranges in about **2.13 s** in
  one warm run (~0.84 ms/range); the largest files measured 80–300 ms for their
  candidate ranges. This is acceptable-on-save territory for ordinary files, not
  evidence for per-keystroke reparsing, and it may justify parser reuse/caching;
- construct-safe coverage is not formatter eligibility until total partition,
  block stability, native/browser projection parity, idempotence, and
  independent GFM-aware gate 3 pass;
- true included ranges return with list/blockquote containers because those are
  disjoint retained ranges with prefix ownership. That is a later container
  slice, not A2.

Recommendation: approve A2 as the four staged slices above, and make the 43 KB
payload plus Unicode scope explicit review decisions. Do not budget an
included-range parser, and do not budget a week for the scanner. Budget the week
for the projection's cross-grammar safety proof.
